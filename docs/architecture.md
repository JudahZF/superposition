# Architecture

## Purpose, status, and boundary

Superposition is a macOS audio host that treats plug-ins as untrusted, latency-sensitive native code. The host process owns session orchestration, device integration, scheduling, UI coordination, persistence, and recovery policy; helpers own the code paths that load VST3 bundles.

This repository contains Phase 0 contracts and substantial later-phase alpha implementation, not a certified product. It has fixed shared-memory protocol/layout types, synthetic and AUHAL-attached feasibility harnesses, helper-only VST3 scanning, retained serial-rack workers, and a duplex product mixer/endpoint composition. The desktop app can select one same-device stereo route, capture input, dispatch audio and bounded MIDI to indexed rack workers, mix validated completions, edit normalized parameters, persist component/controller state, toggle worker-owned native-editor windows, and replace a failed rack worker on its alternate stable bank. The long-running hardware evidence required to claim the Phase 1 gate remains incomplete.

## Rack topology and failure scope

A project is modeled as ordered racks. A rack is the intended isolation and recovery unit: it owns its plug-in chain, routing configuration, parameter scenes, and worker lifecycle. The alpha topology deliberately excludes arbitrary split/recombine paths, feedback, and general plug-in delay compensation.

The product supervisor starts one retained worker per loaded rack and places a gate between that worker and the real-time graph. Explicit rack indices are retained even when only a sparse subset of racks has workers. The gate accepts only a live generation and block ticket. One deadline miss renders rack-local fallback for that block; three consecutive misses close the gate and request recovery. A crash or malformed result closes it immediately. The dispatcher validates stereo block metadata, bounded MIDI and automation, ticket identity, and finite output before contributing a wet buffer. Each rack pre-maps two stable banks. On a worker fault, a lock-free control/callback handshake quiesces that rack, the supervisor reaps the old worker and starts one replacement on the alternate bank, initially bypassing the suspected slot, and the callback switches generations at a block boundary. The retired bank is reset only after the old worker is gone; unaffected racks continue dispatching throughout.

## Device I/O: direct AUHAL

macOS uses the direct AUHAL boundary in `sp-audio-io-macos`; `cpal` is not a workspace dependency. The C shim creates `kAudioUnitSubType_HALOutput`, binds an explicitly selected same-device input/output route, rejects formats outside fixed 48 kHz stereo 128/256-frame operation, captures input through `AudioUnitRender`, and installs an interleaved `f32` playback callback. `ProductRenderer` dispatches that captured block plus callback-safe CoreMIDI events to workers, mixes valid completions, and enforces native callback retirement before Rust drops the renderer. Separate input and output devices still require an aggregate device because the alpha does not perform cross-device clock synchronization or sample-rate conversion.

`cargo xtask device-feasibility --racks <1|2|4|8> --frames <128|256> --duration-seconds <seconds>` attaches that direct AUHAL output callback and executes the shared-memory feasibility path. The control plane creates and heartbeat-validates workers and mappings before callback activation; the callback receives only fixed-layout bank/gate state, preallocated timing histograms, and atomic liveness flags. Each callback publishes every open rack, performs nonblocking completion sweeps until all requests resolve or the absolute 75%-of-period deadline arrives, and then selects rack-local fallback for unresolved work. It returns silence, so no plug-in output reaches the host process. A successful short run proves only that the callback attached and its immediate acceptance checks passed; the report always records `phase1_hard_gate_certified=false`. An optional `--bundle` mode exercises a VST3 inside the attached worker path but is labeled as a non-certifying smoke; the scanner-first VST3 artifact remains separately required.

`cargo xtask device-matrix` runs the eight 1/2/4/8-rack by 128/256-frame cells sequentially. Each cell publishes an atomic JSON/Markdown/manifest triplet whose manifest contains SHA-256 digests for both payloads. The report retains callback proof, device format, requested/observed duration, request→claim, processing, request→completion-publication, completion-publication→host-observation, request→host-observation, observe/dispatch, and full-callback p99.9/p99.99/max histograms, exact threshold values, fatal error codes, overruns, deadline/protocol/exit counters, CPU/energy evidence, and worker process/generation/bank identities. `calibrated_load` and `fault_isolation` are explicit artifact kinds rather than being silently folded into a no-op cell. Each claimed frame size requires a calibrated 8-worker result plus self-crash and hang-after-claim 2-worker fault evidence; the fault record identifies one target rack, proves every remaining rack accepted work before callback retirement, and records the target fallback block as current-or-next relative to the trigger.

`cargo xtask vst3-smoke --sdk "$VST3_SDK_DIR"` delegates fixture discovery to the scanner and only then invokes the worker's one-block Again processor; neither `xtask`, the app, nor the engine loads the SDK bundle. It copies the helper-produced HostChecker result into `target/phase1/vst3-smoke/` as a SHA-256-addressed raw input before atomically publishing the smoke report. `cargo xtask phase1-report` reads only canonical required artifact locations, verifies raw report/Markdown digests, and cannot set `certified=true` without every device matrix cell, both calibrated-load results, all four attached fault-isolation results, and isolated real-VST3 evidence. The required long runs belong on the designated Apple Silicon hardware and remain outside hosted CI.

[ADR 0010](adr/0010-direct-auhal-backend.md) records this deliberate deviation from the original `cpal` recommendation.

## Data and control planes

The data plane uses `#[repr(C)]`, fixed-layout `SharedBank` mappings. A bank contains the protocol header, fixed rack descriptors, and fixed-capacity block slots; it contains no Rust references, heap containers, strings, or Rust enum fields. Payload is written before a release publication, and the peer acquire-loads the state before it reads that payload. Slot tickets carry generation and sequence; a stale completion is rejected rather than mixed.

On macOS, `sp-shared-memory-macos` creates a named POSIX mapping sized to exactly one `SharedBank`, initializes it before handing its name to a worker, and gives the mapping's owner access only through the safe protocol APIs. The product dispatcher has preallocated per-rack output buffers and uses the Darwin continuous clock to bound completion observation. It receives no control IPC and does not launch, log, allocate, or sleep from the callback path.

The separate control plane is reserved for discovery, helper lifecycle, parameters, state transfer, diagnostics, and UI requests. It may use ordinary IPC and persistence, but it cannot be a dependency of callback progress.

Native editor control requests are the only ordinary UI operations that transfer the rack runtime from its processing thread to the worker's initial AppKit thread. That thread owns the top-level `NSWindow`, attaches only its content `NSView` to the VST3 controller, pumps AppKit events, and performs focus, resize, detach, and close. The processing owner drains bounded plug-in resize notifications and forwards only numeric geometry to that AppKit loop. Destructive slot replacement and shutdown also route through the main-thread owner so an attached view is removed before its controller is destroyed. The main application never receives a plug-in view or SDK pointer.

## Package direction and VST3 boundary

`sp-model` defines durable domain types. `sp-protocol` defines versioned wire records. `sp-shared-memory` owns safe fixed-layout and slot primitives, while `sp-shared-memory-macos` owns POSIX mapping and Darwin-clock FFI. `sp-engine` owns graph/gate/mixing foundations. `sp-audio-io` contains platform-neutral endpoint types, and `sp-audio-io-macos` owns the direct AUHAL implementation. `sp-supervisor`, `sp-session`, `sp-midi`, and `sp-ui` remain outside the callback dependency path.

`sp-vst3` is the sole VST3 adapter boundary. Its SDK feature is enabled by `sp-plugin-worker` and `sp-plugin-scanner` only. The main app and `sp-engine` must not transitively reach `sp-vst3`, `vst3`, or `vst3-host`; direct dependency edges remain limited to the helper/adapter chain. No app, engine, model, protocol, session, or UI type may expose VST3 SDK types. `cargo xtask doctor` verifies that dependency rule from Cargo metadata. The scanner and worker helper capabilities are partial foundations, not a general VST3 compatibility assertion.
